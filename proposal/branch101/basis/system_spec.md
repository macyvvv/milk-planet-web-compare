# システム仕様(技術構成・実装制約・セキュリティ要件)

## 1. 技術スタック

| 領域 | 採用技術 | 備考 |
|---|---|---|
| フロントエンド/バックエンド | Next.js(App Router, Server Components, Route Handlers) | 単一アプリ。バージョンは実装着手時点の安定版を固定し、`package.json` にpinする |
| 言語 | TypeScript | strictモード |
| DB | PostgreSQL | マネージドサービスを利用(D-001参照)。バージョンは実装着手時点の安定版 |
| ORM/マイグレーション | Prisma ORM | スキーマは `data_model.md` を正本として生成 |
| 認証 | ユーザー名(login_name)・パスワード + サーバーセッション | パスワードハッシュは Argon2id |
| バリデーション | Zod | サーバー側(Route Handler / Server Function境界)で必須実行 |
| テスト | Node.js組み込みtest runner(単体) + Playwright(E2E) | D-008によりVitestから変更。詳細は `test_strategy.md` |
| UI | レスポンシブ・モバイルファースト・アクセシブルなフォーム部品 | PC専用機能は作らない |

## 2. デプロイ構成(D-001の反映)

```text
[ブラウザ]
   │  proposal/branch101/index.html (静的エントリページ。既存branch1〜5と同じ階層)
   │  → 実アプリへのリンク
   ▼
[実アプリ: Next.js on 別ホスティング(例: Vercel等 実装着手前に確定)]
   │
   ▼
[マネージドPostgreSQL(例: Neon / Supabase等 実装着手前に確定)]
```

- `proposal/branch101/` にはこれまでのbranchと同様、比較サイトから辿れる**静的エントリページ**(概要・
  スクリーンショット・実アプリへのリンク)を置く。GitHub Pagesはこの静的エントリページのみを配信する。
- 実アプリ本体のソースコードは同リポジトリ内(例: `proposal/branch101/app/`)に置くが、**GitHub Pagesへは
  デプロイしない**。Next.jsのビルド・実行・DB接続が可能な別ホスティングへ独立してデプロイする。
- ホスティング先・DBサービスの具体名はPhase 1着手前にユーザーと確定する(アカウント・課金が発生するため)。
- `proposal/index.html`(比較サイトのトップ)に branch101 のカードを追加し、動線を確保する。

## 3. アーキテクチャ制約

- 単一リポジトリ・単一Webアプリ・単一RDBのモジュラーモノリス。マイクロサービス化・別プロジェクトAPIサーバー化はしない。
- ドメインロジックはサービス層(ユースケース関数)に集約し、Reactコンポーネント・Server Function・Route Handlerへ
  直接書かない(`policy.md` 参照)。
- モジュール構成は `architecture.mmd` に従う。

## 4. データベース制約方針

アプリケーションコードだけに整合性を委ねず、DB制約でも保証する(`data_model.md` に詳細)。

- `CREATE EXTENSION btree_gist` を利用し、確定シフトの時間重複・同日複数店舗配置を `EXCLUDE USING gist` で防止
  (D-002)。
- ピリオド期間の重複防止、同時点の有効ログイン名重複防止、同時点の通常所属重複防止は部分一意インデックス /
  排他制約で実装。
- 監査ログ(`audit_logs`)はアプリケーション層でUPDATE/DELETEを行う経路を作らない。DB権限としても、通常の
  アプリケーションDBロールにはUPDATE/DELETE権限を付与しない運用とする。

## 5. 定期実行(ピリオド自動生成)

D-003のとおり、(a)参照時の冪等な不足分生成、(b)ホスティング先のスケジュール実行機能からの事前生成、の
二経路を併用する。いずれも同一のサービス層関数 `ensurePeriodsGenerated()` を呼ぶ。

## 6. セキュリティ要件

- パスワードハッシュ: Argon2id(ソルト付き、パラメータは実装時点のOWASP推奨値)。
- セッション: HttpOnly, Secure, SameSite=Lax(またはStrict)属性付きCookie。HTTPS前提。
- CSRF対策: Server Actionsの組み込み保護、またはRoute HandlerでのCSRFトークン検証。
- XSS対策: Reactの自動エスケープに加え、CSVエクスポート等のユーザー入力を含む出力ではエスケープ・無害化を行う
  (CSVインジェクション対策として、数式として解釈されうる先頭文字 `= + - @` を含むセルは無害化する)。
- SQLインジェクション対策: Prismaのパラメータ化クエリのみを使用し、生SQL文字列結合を行わない。
- ログイン試行レート制限・一定回数失敗時の一時ロック。
- パスワード変更・パスワードリセット完了時に既存セッションを全失効。
- 認証成功・失敗を監査ログへ記録(パスワード自体・初期設定コード自体・セッショントークン自体はログへ出力しない)。
- 管理者向けMFAは初期必須要件にしないが、`sessions` / `user_credentials` のスキーマは将来のMFA要素追加を
  阻害しない構造とする(例: 追加の認証要素テーブルを後から足せる設計)。

## 7. 性能・可用性

- 想定同時利用者数: 最大250、通常はそれより大幅に少ない。
- 一覧取得はページネーションまたは絞り込みを必須とし、N+1クエリを避ける(Prismaの `include`/`select` を明示指定)。
- `period_id` `store_id` `user_id` `date` を含む複合インデックスを主要テーブルに設定(詳細は `data_model.md`)。
- 過剰なキャッシュ基盤(Redis等)は追加しない。
- DB定期自動バックアップ、保持期間設定、復旧手順の文書化・定期復旧テストを行う(詳細は `operations.md`、
  Phase 5で具体化)。

## 8. ログ・監視

- アプリケーションエラー、認証エラー、DB接続エラー、CSVインポート失敗、公開処理失敗、バックアップ失敗を検知できること。
- 機密情報(パスワード、初期設定コード、セッショントークン)をログへ出力しない。

## 9. 環境・設定

- 環境変数(DB接続文字列、セッション署名鍵等)はリポジトリへコミットしない。`.env.example` で必要変数一覧のみ共有。
- 開発環境と本番DBを分離し、本番データを無加工で開発環境へ複製しない(`operations.md` で手順化)。
