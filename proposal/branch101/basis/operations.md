# 運用

想定構成: Next.js(Vercel等) + 永続libSQL。Vercelの一時ファイルDBは本番利用しない。
`DATABASE_URL` と必要な `DATABASE_AUTH_TOKEN` はユーザー側で安全に設定する。

## 1. デプロイ

1. `npm run build` がローカル/CIで成功することを確認する。
2. `npm run migrate:libsql` を対象環境の `DATABASE_URL` に対して実行し、スキーマを最新化する
   (`app/README.md` の手順参照)。
3. アプリケーションをデプロイする(Vercel等、ホスティング先のCI/CD経由)。
4. デプロイ後、`/login` にアクセスできること、および任意の1操作(ログイン等)が
   `audit_logs` に記録されることを確認する。

ロールバック方針: アプリケーションはホスティング先の「前のデプロイに戻す」機能を使う。
DBマイグレーションは後方互換な追加(列追加等)を基本とし、破壊的変更(列削除・型変更)を
含むマイグレーションは、ロールバック用の逆マイグレーションを事前に用意してから適用する。

## 2. 定期運用

- ピリオド自動生成(D-003)は、参照時の冪等生成(`ensurePeriodsGenerated()`)に加えて、
  ホスティング先のスケジュール実行機能から定期的に同関数を呼び出すRoute Handlerを用意する
  (未実装。Phase 6以降の課題として残す — 現状は各画面アクセス時の冪等生成のみで機能している)。
- DB定期自動バックアップは、永続libSQLサービス側の自動バックアップ機能を用いる
  (保持期間はサービスのデフォルト、または要件に応じて延長する。具体的な日数はサービス選定後に確定)。

## 3. 障害対応

| 障害種別 | 検知方法(現状) | 一次対応 |
|---|---|---|
| アプリケーションエラー | ホスティング先のエラーログ/監視(未連携) | エラーログを確認し、`audit_logs` と突き合わせて影響範囲を特定 |
| 認証エラー(大量失敗) | `audit_logs` の `LOGIN_FAILURE`/`ACCOUNT_LOCKED` 件数(未ダッシュボード化) | 特定ユーザーへの攻撃か、システム障害かを切り分け |
| DB接続エラー | Prismaのエラーログ(`lib/db.ts` の `log` 設定) | libSQLサービスの稼働状況を確認 |
| CSVインポート失敗 | `csv_import_jobs.status = FAILED`/`errorSummary` | 該当ジョブのエラー内容を確認し、CSVを修正して再アップロード |
| 公開処理失敗 | トランザクション失敗時は例外がServer Actionへ伝播 | `/admin/publications` で公開状態を再確認し、再実行 |
| バックアップ失敗 | マネージドPostgreSQLサービスの通知(未連携) | サービス側のダッシュボードを確認 |

外部監視サービス(Sentry等)との連携、Slack等への通知連携は未実装。Phase 6以降の検討課題とする
(元指示書の禁止事項には抵触しない範囲で、必要最小限のものを追加検討する)。

## 4. バックアップ・復旧

- バックアップ: libSQLサービスの自動バックアップ機能に依存する(具体的な保持日数は
  サービス選定後にユーザーと確定する)。
- 復旧手順: (1) 新しいDBインスタンスをバックアップから復元 (2) `DATABASE_URL` を復元先に切り替え
  (3) アプリケーションを再デプロイ (4) `/login` 等での疎通確認。この手順は少なくとも1回、
  本番投入前に実地でリハーサルすること(Phase 6 DoD項目)。
- 開発環境への本番データ複製: 無加工複製は行わない。個人情報(表示名・読み仮名等)を含むため、
  開発時はシードスクリプト(未実装)による架空データ、または氏名列のみマスキングしたエクスポートを使う。

## 5. CSV退避・復旧

DB障害等でアプリケーションが利用不能な間の緊急対応として、`/admin/csv` の各エクスポート
(特にキャスト一覧・確定シフト・提出状況)を定期的にダウンロードし、店舗側でオフライン保管する
運用を推奨する。自動化(定期エクスポートのメール送信等)は初期版では実装しない
(元指示書25.2「メール送信」は対象外)。

## 6. 未確定・今後の課題

- 永続libSQLサービスの具体名とバックアップ条件の確定
- 一次対応者・エスカレーション連絡フロー(Slack/電話等、ユーザー側の運用ルールに依存)
- バックアップ保持期間・復旧テスト頻度の具体的な数値
- 外部監視・通知サービスとの連携要否

## 7. 初期SUPER_USER

1. 永続libSQLへ全migrationを適用する。
2. `DATABASE_URL` と必要なら `DATABASE_AUTH_TOKEN` を設定する。
3. `npm run bootstrap:su` を一度だけ実行する。
4. 一度だけ表示される初期設定コードをSU本人へ安全な経路で伝える。
5. SU本人が72時間以内に `/initial-setup` で `admin` とコードを入力し、パスワードを設定する。
6. `/admin/users` と `/admin/audit` でACTIVE化と監査記録を確認する。

ユーザーが1件でも存在すればbootstrapは拒否される。全SU喪失時の復旧手段として再利用しない。
