# 品質方針・設計原則・非目標

## 1. 最上位方針

1. **業務データの正本と履歴の再現性を、実装の簡便さより優先する。**
   希望シフト・確定シフト・公開版は別データとして保持し、後から「あの時点で何が公開されていたか」を再現できることを
   機能追加より優先する。
2. **入力負荷・管理負荷・保守負荷を抑える。** 機能追加そのものを目的にしない。元指示書にない機能は追加しない。
3. **権限境界をサーバー側で必ず再検証する。** クライアント側の表示制御は利便性のためであり、権限判定そのものではない。
4. **将来拡張を理由に初期版へ不要な複雑性を導入しない。** マイクロサービス化・キュー・キャッシュ基盤・AI自動化は
   初期版で採用しない(第2章「禁止事項」を参照)。

## 2. 設計原則

- **モジュラーモノリス。** 単一Next.jsアプリ・単一PostgreSQL。モジュール境界はディレクトリと呼び出し規約で表現し、
  物理的なサービス分割はしない。
- **ドメインロジックはサービス層に集約する。** React Server Component・Server Function・Route Handlerに業務ルールを
  直接書かない。これらは「入出力の窓口」であり、判定・計算・状態遷移はサービス層(ユースケース関数)が持つ。
- **DBで保証できる整合性はDBにも持たせる。** アプリケーションコードだけに委ねない(一意制約・排他制約・CHECK制約)。
- **追記専用ログと可変な業務データを区別する。** 監査ログ(audit_logs)・公開版(published_shift_entries)は
  UPDATE/DELETEを行わない。可変な業務データ(希望下書き等)は版(バージョン)テーブルで変更前後を残す。
- **希望データと確定データは異なるテーブル・異なるライフサイクルを持つ。** 管理者が希望データを書き換えて確定結果に
  変換する実装は禁止する。
- **同じ保存ロジックを画面ごとに重複実装しない。** 日付別ビューとキャスト別ビューは同一のユースケース関数を呼ぶ。
- **時刻は保存前に絶対日時へ正規化する。** 画面表示用の文字列(「25:00」等)をそのままDBへ保存しない。

## 3. 非目標(初期版でやらないこと)

元指示書 1.2 節の禁止事項をそのまま非目標として採用する。

- マイクロサービス化 / APIサーバーの別プロジェクト化
- Kubernetes / Redis / メッセージキュー / Elasticsearch の導入
- LINE API連携(文章生成とコピーのみ)
- AIによる自動シフト作成
- 勤怠・打刻・給与
- 必要人数・人員不足判定
- キャスト名の主キー化(内部識別子は不変UUID)
- 希望シフトの上書きによる確定シフト化
- 監査ログの更新・削除
- 管理者によるキャスト本人希望の代理提出(CSV含む。CSVでの出勤希望投入はSUPER_USER限定の緊急復旧手段とし、
  理由必須・監査対象とすることで「代理入力禁止の抜け道」にしない)
- 平文パスワード保存
- クライアント側のみでの権限判定
- 表示用時刻文字列のDB直接保存

## 4. 品質基準

- 単体テスト・DB統合テスト・E2Eテストを備える(詳細は `test_strategy.md`)。
- 250同時利用を想定した基本的な性能配慮(N+1回避、適切な複合インデックス、ページネーション)。ただし過剰な
  キャッシュ基盤は追加しない。
- 未解決TODO・仮実装・ダミー認証・ハードコードされた権限を残したまま完了扱いにしない(DoDは元指示書27章参照)。
