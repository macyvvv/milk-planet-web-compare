ユーザー操作に影響する事項はユーザー承認前に明示する方針(元指示書28章)に従う。

## D-000: 設計資料フェーズの進め方

- **論点**: `basis/` 全13資料を一度に詳細まで作り込むか、段階的にするか。
- **該当要件**: 元指示書 1.1「実装開始条件」。
- **問題**: 全資料を初回から詳細化すると、後続の承認プロセスで手戻りが大きくなる可能性がある。
- **選択肢**:
  A) 13資料すべてを詳細まで作成してから提示。
  B) 主要4資料(requirements/data_model/state_transitions/authorization_matrix)を詳細作成し、他は骨子のみで
     提示、承認後に screen_spec/test_strategy/operations 等を埋める。
- **推奨案**: B(ユーザー合意済み)。
- **推奨理由**: 業務フロー・データ正本・権限・履歴という「後から変えにくい」部分を先に固め、画面仕様やテスト
  戦略のような「実装と一緒に磨き込む」部分は承認後にする方が手戻りが少ない。
- **影響範囲**: `screen_spec.md` `test_strategy.md` `operations.md` は現時点で骨子のみ。
- **残存リスク**: 骨子段階では画面遷移の細部やテストケースの網羅性は未検証。Phase 1着手前に再レビューする。

## D-001: ホスティング方式とGitHub Pagesとの関係

- **論点**: `proposal/branch101` を既存の `branch1〜5` と同様に配置し、ブラウザで見られるようにしたいという要望
  (ユーザー回答: 「github pagesに入れてこれも一緒にwebブラウザで見られるように…proposalの下で、今までのbranchと
  同様に作成して欲しい」)と、元指示書2章が要求する技術構成(Next.js Server Components / Route Handlers、
  PostgreSQL、Argon2idによるサーバーセッション認証)が両立しない。
- **該当要件**: 元指示書 2.1/2.2(採用技術)、および配置に関するユーザー回答。
- **問題**: GitHub Pagesは静的ファイル配信のみで、Node.jsサーバー実行・DB接続・サーバーセッションを持てない。
  branch1〜5は静的サイトなのでGitHub Pagesと相性が良いが、branch101は業務システムであり同じ配信方式は使えない。
- **選択肢**:
  A) 要求どおりGitHub Pagesのみで完結させる → 認証・DB・監査ログをブラウザローカルのみで実装することになり、
     元指示書の非機能要件・セキュリティ要件・監査要件を満たせない。実質的に別物(モック)になる。
  B) 実データ・認証を持つ実アプリは別ホスティング(例: Vercel + マネージドPostgreSQL)にデプロイし、
     `proposal/branch101/` にはこれまでのbranchと同じ「比較用エントリページ」を置いて、実アプリへの動線を提供する。
     `proposal/index.html` の比較UIにも branch101 のカードを追加する。
  C) branch101用に別リポジトリを新設し、このリポジトリとは切り離す。
- **推奨案**: B。
- **推奨理由**: ユーザーが「このrepoで開始している」「今までのbranchと同様に」と明言しており、比較サイトの一部として
  ブラウザから辿れることを重視している。Bであれば、比較サイトからのアクセス動線という要望を満たしつつ、
  元指示書が要求するセキュリティ・監査・DB整合性を犠牲にしない。Cは要望(このリポジトリで、branchと同様に)に反する。
  Aは非機能要件・セキュリティ要件を満たせず、元指示書の目的(履歴を失わない業務システム)そのものを損なう。
- **影響範囲**: `system_spec.md` のデプロイ構成、`proposal/branch101/index.html`(実装フェーズで作成する静的エントリ
  ページ)、`proposal/index.html` への導線追加。実アプリ本体(Next.jsコード)は `proposal/branch101/app/` のような
  形でリポジトリ内にソースとして置くが、GitHub Pagesではなく別サービスにデプロイする。
- **残存リスク**: 実アプリのホスティング先(Vercel等)のアカウント作成・環境変数設定・DB(例: Neon / Supabase等の
  マネージドPostgreSQL)の契約はユーザー側の対応が必要になる。具体的なサービス選定はPhase 1着手前に別途確認する。

## D-002: 確定シフトの時間重複防止をDB制約で行う方式

- **論点**: 「1キャストの確定勤務時間重複防止」「同日複数店舗勤務防止」をDB制約で保証する具体的手段。
- **該当要件**: 元指示書17章(DB制約)、13.2(同日複数店舗配置禁止)。
- **問題**: PostgreSQL標準機能だけでは「同一キャストの時間帯重複禁止」をUNIQUE制約で表現できない。
- **選択肢**:
  A) アプリケーションコードのみでチェックする(トランザクション内でSELECT→検証→INSERT)。
  B) PostgreSQLの `btree_gist` 拡張を有効化し、`EXCLUDE USING gist` 制約で
     `(user_id WITH =, tstzrange(start_at, end_at) WITH &&)` の重複を防止する。
- **推奨案**: B。
- **推奨理由**: `policy.md` の方針「DBで保証できる整合性はDBにも持たせる」に合致する。`btree_gist` はPostgreSQL
  標準拡張であり、Redis等の新規インフラ導入には当たらない。アプリ側チェックのみでは競合状態(同時保存)で
  重複をすり抜ける可能性があるが、DB制約なら確実に防げる。
- **影響範囲**: `data_model.md` の `confirmed_shifts` 制約定義。マイグレーションで `CREATE EXTENSION btree_gist`
  が必要(禁止インフラには該当しないため許容)。
- **残存リスク**: マネージドPostgreSQLサービスによっては拡張の有効化に管理者権限が必要な場合がある。Phase 1で
  ホスティング先決定後に確認する。

## D-003: ピリオド自動生成の実行方式

- **論点**: 「将来12か月分を定期的に自動生成するか、参照時に不足分を冪等に生成する」の具体的方式。
- **該当要件**: 元指示書7.1。
- **問題**: メッセージキュー等の常駐ジョブ基盤は禁止されている一方、定期実行の仕組みは何らかの形で必要。
- **選択肢**:
  A) キャスト・管理者がピリオド一覧や出勤希望画面にアクセスした際、必要なピリオドが存在しなければその場で
     冪等に生成する(get-or-create)方式のみ。
  B) Aに加えて、ホスティング先のスケジュール実行機能(例: Vercel Cron)から同じ生成関数を定期的に呼び出す
     Route Handlerを用意し、事前生成しておく。
- **推奨案**: B。
- **推奨理由**: Aのみだと「誰もアクセスしていない将来ピリオド」が存在せず、管理者がイベント登録しようとした
  瞬間まで対象ピリオドが見えない体験になる。Bはプラットフォーム標準のスケジュール機能(単なるHTTPトリガー)を
  使うだけで、キューや常駐プロセスを追加しない。生成関数自体は冪等なのでAの経路と共存できる。
- **影響範囲**: `system_spec.md`(定期実行の仕組み)、`data_model.md` の `periods` 一意制約(重複生成防止は
  DB制約で担保するためA/Bどちらの経路でも安全)。
- **残存リスク**: ホスティング先が確定していないため、Cron機能の有無・上限をPhase 1で確認する。

## D-004: ログイン名の一意性判定に含める状態

- **論点**: 「同時点で有効なユーザー間ではログイン名を一意とする」の「有効」の範囲。初期設定コード発行済みだが
  パスワード未設定のユーザーを含めるか。
- **該当要件**: 元指示書5.1、5.2。
- **問題**: 「有効」を `ACTIVE` のみと解釈すると、管理者がキャストA「あい」を事前登録した直後(まだ初期設定コード
  未使用)に、別の管理者が同名の別人「あい」をもう一件事前登録できてしまい、初期設定コードの奪い合い・誤登録が
  起きうる。
- **選択肢**:
  A) 一意制約の対象を `ACTIVE` のみとする。
  B) `PENDING_SETUP`(事前登録済み・初期設定未完了)と `ACTIVE` の両方を対象とする。
- **推奨案**: B。
- **推奨理由**: 5.2節の目的は「第三者が未登録のキャスト名を取得することを防ぐ」ことであり、登録直後のなりすまし
  ・誤登録防止にも同じ考え方を適用するのが自然。
- **影響範囲**: `data_model.md` の `users.user_status` 定義と部分一意インデックス条件。
- **残存リスク**: なし(実装コストへの影響は軽微)。

## D-005: 「公開後変更」と「再公開」を別操作にするか

- **論点**: 公開後にキャストへ見えている確定シフトを変更した際、その変更を即座に新しい公開版として反映するか、
  変更の記録と公開版の更新を別操作にするか。
- **該当要件**: 元指示書13.4(公開版生成)、13.5(公開後変更)。
- **問題**: 元指示書は「公開後変更を許可する」「変更理由・前後・操作者・日時・連絡済み状態を必須とする」
  「変更履歴画面から差分を確認できる」を要求するが、変更のたびに必ず新しい公開版(`shift_publications`)を
  生成すべきかは明記されていない。
- **選択肢**:
  A) 公開後の `confirmed_shifts` 編集を保存した瞬間に、自動的に新しい `shift_publications` 版を生成する
     (変更=即再公開)。
  B) 公開後の編集は `confirmed_shift_versions`(`is_post_publication_change=true`)に記録するのみとし、
     管理者が明示的に「再公開」操作を行った時だけ新しい `shift_publications` 版を生成する。
- **推奨案**: B。
- **推奨理由**: 管理者が複数キャスト分の細かい調整を連続して行った後、まとめて1回「再公開」したいケース
  (例: 当日3件変更してから一斉に反映)が業務上あり得る。Aだと変更のたびに公開版が増殖し、「連絡済み状態」を
  どの粒度で管理するかも曖昧になる。Bなら「今どの変更が未反映か」を明確にでき、公開操作自体は他の状態遷移
  (CONFIRMED→PUBLISHED)と同じ操作性(=公開ボタン)に統一できる。
- **影響範囲**: `state_transitions.md` 5章、`screen_spec.md`(公開後変更画面に「未反映の変更」表示が必要)、
  `authorization_matrix.md`(再公開操作の権限)。
- **残存リスク**: 「変更したのに再公開を忘れる」運用ミスが起きうる。ダッシュボードに「未反映の公開後変更件数」
  を表示するなどの緩和策をPhase 4で検討する(承認事項として明示)。

## D-006: キャスト事前登録・初期設定コード発行・パスワード再設定許可の権限レベル

- **論点**: 新規キャストの事前登録、初期設定コード発行、パスワード再設定の許可を STORE_MANAGER/DEPUTY にも
  与えるか、AREA_MANAGER以上に限定するか。
- **該当要件**: 元指示書4.2(STORE_MANAGER権限一覧)と14.5(アカウント管理画面の機能一覧)の間に齟齬がある。
- **問題**: 4.2のSTORE_MANAGER権限一覧には「管理対象店舗のキャストのみ閲覧」「イベント登録・変更」「締切設定」
  「提出状況閲覧」「未提出者一覧生成」「確定シフト作成・編集・公開」「CSV入出力」しか列挙されておらず、
  キャストの新規登録・初期設定コード発行・パスワード再設定許可は含まれていない。一方14.5の「アカウント管理」
  画面機能一覧にはこれらが列挙されているが、どのロールがアクセスできるかは明記されていない。
- **選択肢**:
  A) 4.2の明示列挙を厳密に採用し、STORE_MANAGER/DEPUTYはキャスト登録・コード発行・パスワード再設定許可を
     一切行えない(AREA_MANAGER以上に限定)。
  B) 14.5のアカウント管理機能はSTORE_MANAGER/DEPUTYにも開放し、自店舗キャストの範囲でキャスト登録・コード
     発行・パスワード再設定許可を行えるようにする。
- **決定案**: B(ユーザー承認済み)。
- **決定理由**: 実運用において、新規キャスト登録やパスワード忘れのたびにAREA_MANAGER/SUPER_USERが対応するのは運用負荷が高いため、各店舗の店長に委譲することが妥当と判断された。
- **影響範囲**: `authorization_matrix.md` の該当行を更新済み。`screen_spec.md` の `/admin/users` アクセス制御に反映する。
- **残存リスク**: なし。

## D-007: period_store_settings への events_confirmed_at / events_confirmed_by 追加

- **論点**: `state_transitions.md` は PREPARING→OPEN の遷移条件として「管理者が『イベント確認済み』
  操作を行っている(REQ-EVENT-003)」を要求するが、承認済みの `data_model.md` 初版の
  `period_store_settings` にはこれを記録する列がなかった。
- **該当要件**: REQ-EVENT-003、元指示書9.3。
- **問題**: 列がないと「イベント確認済み」を判定・監査する手段がなく、受付開始のガード条件を
  実装できない。承認済みデータモデルの単純な記入漏れ。
- **対応**: `period_store_settings` に `events_confirmed_at TIMESTAMPTZ NULL可` と
  `events_confirmed_by UUID NULL可(FK→users.id)` を追加(`data_model.md`・`schema.prisma`同時反映)。
- **影響範囲**: 新規テーブルではなく既存テーブルへの追加列のみ。他モジュールへの影響なし。
- **残存リスク**: なし。実装中に発見した記入漏れの補完であり、業務フロー・権限・履歴方式の変更は伴わない。

## D-008: テストランナーをVitestからNode組み込みのtest runnerへ変更

- **論点**: `system_spec.md` はテストツールとして「Vitest等」を想定していたが、実装時にVitestが
  このリポジトリのパスで動作しないことが判明した。
- **該当要件**: 元指示書2.1(テスト構成)、`test_strategy.md`。
- **問題**: リポジトリの絶対パスに `#_amagi` というディレクトリ名が含まれる。Vite(Vitestの基盤)は
  内部でファイルパスをURLへ変換する際に `#` をURLフラグメント区切りとして誤解釈し、`#`より前の
  パスを丸ごと欠落させる既知の不具合を持つ。実際に `npx vitest run` はテストファイルを
  `Cannot find module '/lib/modules/periods/period-dates.test.ts'`(絶対パスの `#` より前が消失)
  として見失い、実行不能だった。同種の不具合はTailwind CSS v4のネイティブエンジンでも発生し
  D-002とは別にpostcss構成をv3系へ切り替える対応を行っている(`app/README.md`「既知の環境依存
  事項」参照)。
- **選択肢**:
  A) ユーザーにディレクトリ名の変更(`#_amagi` → 別名)を依頼する。
  B) Vite系ツール(Vitest)を避け、Node.js組み込みの `node --test` + `node:assert/strict` を
     単体テストに採用する。
- **推奨案**: B(このセッションで採用済み)。
- **推奨理由**: ディレクトリ名の変更はこのリポジトリの既存コミット履歴・他のbranch(1〜5)・
  GitHub Pages運用に影響する可能性がある改変であり、シフト管理システムの実装作業の範囲を超える。
  Node 24は型注釈の除去(type stripping)を標準でサポートしており、`.ts` ファイルをそのまま
  `node --test` で実行できるため、追加の変換ツールなしでVitestの代替として機能する。
- **影響範囲**: `system_spec.md`(テストツール記載をNode組み込みtest runnerへ更新)、
  `test_strategy.md`(実行コマンド)、`package.json` の `test` スクリプト。単体テストの書き方は
  `describe/it` + `assert.equal` 等(Vitestの `expect().toBe()` とは構文が異なる)。
- **残存リスク**: Node組み込みrunnerはパスエイリアス(`@/*`)やDBモック等の高度な機能を持たない
  ため、DB統合テスト(`test_strategy.md`区分2)は別途方針が必要(D-001のホスティング確定後に
  実DBを使う統合テストの実行方法を再検討する)。

## D-009: availability_submissions への last_reopen_deadline_at 追加

- **論点**: REQ-AVAIL-010「個別的な変更は、管理者が受付を個別再開し…理由・期限…を監査ログへ保存する」
  の「期限」を、監査ログだけでなく `availability_submissions` 自体にも保持するか。
- **該当要件**: REQ-AVAIL-010、state_transitions.md 2章(個別再開)。
- **問題**: 期限を監査ログのみに記録すると、システムが「今この提出は再提出可能か」を判定する際に
  毎回監査ログを走査する必要が生じ、非効率かつ実装が複雑になる。D-007と同種の記入漏れ。
- **対応**: `availability_submissions` に `last_reopen_deadline_at TIMESTAMPTZ NULL可` を追加。
  個別再開時にこの値を設定し、`now() > last_reopen_deadline_at` になれば自動的に編集不可
  (LOCKED相当)として扱う。
- **影響範囲**: 新規テーブルではなく既存テーブルへの追加列のみ。
- **残存リスク**: なし。D-007と同様、業務フロー・権限・履歴方式の変更は伴わない補完。
